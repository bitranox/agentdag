# Probe: SlopCodeBench, the corrected pair

Two arms on the same 17 checkpoints as the calibration arm
(`docs/probes/2026-09-04-slopcodebench-control.md`), under a loop that no longer hides from the
agent what a developer would know: a single-agent **corrected control**, and an agentdag
**coordinator**. This document is written and committed before the corrected control's first
counted checkpoint runs. Everything above the divider is frozen from that moment; results go
below it.

## Pre-registration

### Why a corrected pair, and what "corrected" means

The calibration arm found that the control repaired zero carried-forward defects across 17
checkpoints, and read at source that the harness loop gave it no way to: no evaluation result is
ever fed back, the context is reset per checkpoint, the prompt carries only that checkpoint's
delta spec, and the prompt says "That is all you need to do." A coordinator run under the same
loop would be equally blind, so the comparison would be blind to the one thing decomposition
could plausibly buy here.

Decided with the user on 2026-09-04 (three options, one chosen): both arms get **the information
a real developer has, with no leakage of the hidden tests**. Concretely, two data artifacts and
no harness code change:

1. A **derived catalog** in which `checkpoint_N.md` carries parts 1 to N of the specification,
   the current part marked NEW and the earlier ones marked already implemented. Generated by
   `scripts/scb_cumulative_catalog.py` from the installed catalog (SCBench v1.0, commit
   `4d38d300059667d57e43c31969bc455f5c338b52`); `tests/`, `solutions/` and `config.yaml` are
   byte-identical to the source, so the scorer is unchanged. Selected at launch by exporting
   `SCBENCH_PROBLEMS_PATH`, which the harness validates and records in the run's
   `problem_catalog.json` as `commit=<that path>`.
2. A **prompt template**, `scripts/scb_prompts/whole-spec.jinja`, which is the benchmark's own
   `just-solve` text with "That is all you need to do." removed and three sentences added: the
   specification has several parts; the part marked NEW is what this checkpoint adds and every
   earlier part must keep working exactly as specified, the specification as a whole is what
   counts; the agent may write and run its own tests to check that. Lines 2 to 7 of the template
   are byte-identical to `just-solve`.

Rejected, and why: feeding hidden test results back (leaks the benchmark's tests, makes repair
trivial for either arm, and the numbers stop meaning what the leaderboard's mean); keeping
conversational context across checkpoints (a second dimension of difference between the arms,
and a patch to the harness runner, where the reset is hardcoded).

The hidden tests stay hidden. Neither arm is told what failed. What the corrected loop opens is
self-verification, which either arm may do and the calibration arm's control did not.

### What is measured

Per checkpoint, the calibration document's quantities unchanged: `strict_pass_rate`,
`core_pass_rate`, `isolated_pass_rate`, cost and duration as the harness records them, tokens
recorded separately, and peak single-request prompt occupancy. Two readings are added:

| Quantity     | Definition                                                                                                               |
|--------------|--------------------------------------------------------------------------------------------------------------------------|
| `new tokens` | `input + cache_write` summed over the checkpoint: the protocol's cost unit, cache reads excluded                         |
| `repaired`   | `inherited(n-1) + own(n-1) - inherited(n)`, defined only where checkpoint n carries a regression suite; `None` otherwise |

where `own` and `inherited` split a checkpoint's failed tests by the checkpoint they originated in
(the harness keys each test group `<origin checkpoint>-<category>`). `repaired` is `None`, not
0, for the first checkpoint of a problem, for a checkpoint with no regression suite
(`dynamic_config_service_api` checkpoints 3 and 4), and for a checkpoint whose predecessor was
not evaluated (the reading would otherwise be a two-checkpoint delta): "not measurable" and
"measured as zero" are different answers. A NEGATIVE value is meaningful too: it means a test of an earlier part that
passed at the previous checkpoint fails now, so the checkpoint broke old behaviour rather than
repairing any; it is reported as measured, not clipped to zero. Both readings are computed by `scripts/slopcodebench_readings.py`, never by
eye.

**Per arm:** `S`, the count of the 17 checkpoints with `strict_pass_rate == 1.0`; `C`, the mean
`core_pass_rate` over 17; mean `strict_pass_rate`; the repair total over the checkpoints where it
is defined; total new tokens; total cost.

**The pair's quantity, per the rank 05 decision: the score curve at a shared ceiling.** For each
arm, the running count of strict-perfect checkpoints against cumulative new tokens, in the fixed
checkpoint order below. "Cost to a threshold" is the cumulative new tokens at which an arm's
running count first reaches k, for every k either arm reaches. The final S and C per arm and the
per-checkpoint pairs are reported alongside; no single number is the verdict.

### Coordinator settings, decided 2026-09-04 with the user (four questions, one at a time)

1. **Runaway token guard:** `run_limits.tokens_per_row` 1,200,000 per checkpoint run, in
   agentdag's charged unit (input + cache creation + output per model row). About 3x the
   calibration arm's heaviest checkpoint in that unit, and the ceiling the spec rounds used. On
   exhaustion the run suspends at `a_budget` and the checkpoint ends normally; the event is
   recorded per checkpoint. The control has no equivalent guard, only its 100 turns; this is a
   guard against an unattended runaway, not a shared ceiling, and the write-up says so.
2. **No harness wall-clock timeout on either arm.** Held fixed with the calibration arm, which
   ran with none. The coordinator's own per-node deadlines stand as its structure.
3. **`kernel.deny_bash = ["git push", "gh pr", "gh release"]`.** The default list also denies
   `curl -X POST`, `curl --data` and `wget --post`; the calibration control used exactly those
   four times on `dynamic_config_service_api` to exercise the API it was building. A node that
   cannot do that loses a checkpoint for a reason unrelated to decomposition.
4. **`kernel.parallel = 8`**, the default and the setting every earlier agentdag arm ran with.
   `plan-goal` works in one shared directory, so concurrent work nodes can collide there; that is
   a coordinator property the comparison correctly charges to it.

Decided earlier the same evening: **coordinator nodes get the full CLI tool set** rather than
agentdag's default six (the user's call, against my recommendation of six on both arms). The
control's CLI advertises 25 tools including `Task`; the calibration arm never used `Task`
(Bash 549, Write 3, Read 1 across 17 checkpoints). Consequence accepted and pre-registered: a
node may fan out sub-agents via `Task`, so before the arm counts, a probe must show a
`Task`-using node's sub-agent spend inside that node's own terminal usage; if it does not, the
per-node reading undercounts and the arm does not run until that is fixed.

Decided by me, recorded here so the write-up cannot drift from it:

- **Gate command:** `kernel.gate_command = [".venv/bin/python", "-m", "pytest", "-q"]`, run in
  `/workspace`. pytest exits 5 when it collects nothing, which is a real gate failure: the node
  wrote no tests. The planner's brief states what the gate runs.
- **CLI version:** the claude-agent-sdk the coordinator dispatches through prefers its own bundled
  CLI (2.1.259 in the pinned SDK) over the one on PATH. The coordinator image removes the bundled
  binary so nodes run the container's `claude` 2.1.260, the same as both controls; every node
  transcript's init line must report `claude_code_version` 2.1.260, checked before the arm
  counts. Fallback if the SDK refuses the PATH binary: pin 2.1.259 on BOTH corrected arms and
  record the deviation from the calibration arm.
- **Workspace:** the coordinator's plan works directly in `/workspace` (agentdag's `plan-goal`
  gains a `workspace` argument for it). Only what is in `/workspace` when the harness snapshots
  is scored, and the coordinator's run directory lives under the container's home, outside the
  snapshot, so no journal, transcript or credential file can enter the scored tree.
- **Turn bound asymmetry, recorded not removed:** a control process at 100 turns stops; an
  agentdag node at 100 turns hands over to a continuation (up to `thresholds.max_continuations`).
  That is agentdag's structure and part of what is measured.
- **Steps** for the coordinator are counted the way the harness counts them for the control:
  distinct assistant `message_id` across all node transcripts of the checkpoint.
- **Suspension is a normal end.** A checkpoint run that suspends at `a_planning` (planner
  exhausted) or `a_budget` (guard hit) ends the checkpoint; whatever landed in `/workspace` is
  scored; the suspension and its node are recorded per checkpoint. It is not an error and not a
  zero by fiat.
- **Cost units are never mixed.** agentdag's `charged_tokens` excludes cache reads; the harness's
  `cost` comes from the CLI's own `total_cost_usd`, which includes them. The coordinator's cost
  is the sum of its nodes' `total_cost_usd`, the same unit the control reports.

### Bands and decision rules

**Corrected control, on its own, read before the coordinator arm runs:**

| Band      | Condition | Verdict                                                                                                                                                      |
|-----------|-----------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|
| SATURATED | `S >= 12` | The corrected loop alone closes the gap. Subset refuted for the pair; the coordinator arm moves to the catalog's Hard problems under a new pre-registration. |
| USABLE    | `S <= 11` | Proceed to the coordinator arm on this subset.                                                                                                               |

The corrected control's `S` against the calibration arm's 5 is a READING about the loop fix, in
either direction; it is not a verdict on anything.

**The pair:** no band. The score curve, the per-checkpoint pairs, the repair totals and the final
S and C per arm are reported side by side with the cost each arm paid. With one run per arm the
pair measures SEPARATION, not causation, and the write-up must say so; a replication decision
follows the pair and may not be used to revisit this document.

### Void conditions, applying to every run of either arm

A run meeting any of these is VOID for the affected problem: not tallied, not reported as a null
result, re-run after the cause is fixed.

1. Any checkpoint whose tests did not execute (harness error, docker failure, collection error).
2. Any checkpoint where the agent terminated on an auth failure. A rate limit is reported as an
   auth failure on this harness and no field distinguishes them; confirmed out of band first.
3. Any checkpoint where a CLI process hit the 100-turn bound with work in flight, recorded per
   checkpoint. (For the coordinator: a node that hands over at 100 turns is NOT this; a node
   whose continuation chain is exhausted is recorded as such.)
4. Any problem during which the OAuth token expired. Problems run one at a time and the token is
   refreshed between them whenever its remaining validity is shorter than the problem's expected
   duration, which the calibration arm's durations supply.
5. Coordinator only: a checkpoint whose harness `diff.json` is empty while the journal shows a
   work node that completed, which means the work did not land in `/workspace` before the
   snapshot. That is an adapter defect, not a coordinator score.

### Conditions recorded per problem

`uptime` load averages at each problem's start and end, the token expiry at launch, and the
container's `claude --version`. The calibration arm ran under another session's nice-19
embedding job for most of its duration; whether the same holds here is recorded, not assumed.

### What this document does not do

It does not settle whether the pair generalises beyond this subset, does not pre-register a
Hard-problem arm, and does not decide replication. Those follow the pair's result.

**It still never goes back.** With the whole specification in front of it, told that every

#### Conditions the readings were taken under

- **Host load.** `arm.log` records load averages of 29.6 at `circuit_eval`'s start and 20.7 at
  its end, 25.7 and 24.2 around `database_migration`, and 24.2 and 22.1 around
  `dynamic_config_service_api`, on a 16-CPU host. The per-checkpoint `seconds` column is not
  comparable to a quiet-host arm without this caveat; cost and token readings are unaffected.
- **CLI version and model.** Every `init` event in every stream reports `claude_code_version`
  2.1.260 and model `claude-opus-5`, matching the held-fixed table.
- **Tool use.** Across the 17 checkpoints the agent invoked Bash 527 times, Monitor 7 times
  (all on `circuit_eval` 7 and 8), Write 6, Edit 4 and Read once. The calibration arm never
  started a background task; this one did, and that is what put checkpoint 8 over the bound.
  `Task` was never used.

#### Two premises corrected by the measurement, recorded for the pair

- The pre-registration's turn-bound asymmetry ("a control process at 100 turns stops") is
  wrong as written. Read at source in the harness (`agent_runner/agent.py:run_checkpoint`,
  `agents/claude_code/agent.py:retry`), a process that reports a max-turns error raises an
  `AgentError`, and the harness retries with `--continue` and "Continue from where you left
  off." up to `max_retries` more times, default 2. The control therefore also continues past
  100 turns, up to three processes per checkpoint; what it cannot do is carry a background task
  across the boundary. The pair's write-up must state the asymmetry this way.
- A retried checkpoint is unmeasurable on cost and tokens from the harness's record alone: the
  retry replaces the stream and the cost figure. Void condition 3 stands on its own reasoning,
  but this is a second, independent reason such a checkpoint cannot enter a tally.
