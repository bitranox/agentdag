# Probe: agentdag on `agentswarm`'s `spec` case, round 1

The follow-up the `defects` round could not be: that case SATURATED for both arms at 20/20 and
19/20, so it separated nothing. `spec` is the non-saturating candidate - 81 hidden tests, a
measured floor of 0 and a measured ceiling of 81, and a task text that says outright there is
"more here than one agent can finish".

Run under `agentswarm/docs/evaluation-protocol.md`, reported in the form
`agentswarm/docs/agentdag-comparison-handover.md` specifies.

**Everything above the divider was written before the run started and is not edited afterwards.**

## Pre-registration

### What is being compared

agentdag's `plan-goal` workflow against a single Claude agent in one context, on the same case,
the same seeded material, the same ceiling and the same deadline.

### Held fixed

| Setting            | Value                                                                  |
|--------------------|------------------------------------------------------------------------|
| case               | `spec`, agentswarm commit `071f36c`, `max_score` 81                    |
| visible gate       | `pytest tests/ -q` - 92 seeded tests, green on the untouched stubs     |
| new-token ceiling  | 1,200,000, shared by both arms                                         |
| wall-clock ceiling | 2400 s, shared by both arms                                            |
| worker model tier  | sonnet in both arms                                                    |
| scheduler parallel | 8 (raised from the shipped 2 before the counted run - see below)       |
| stop condition     | whichever of the two ceilings comes first; never the system's own call |
| runs per arm       | 1                                                                      |

### The run was restarted once, before any result existed

A first attempt began under the shipped `parallel = 2` and was ABORTED at 31,515 tokens, before any
node finished and before any score was computed. Its run directory is kept as
`spec-runs-dag-ABORTED-parallel2`. The reason: its plan was a SEVEN-wide independent fan-out, and
`parallel = 2` would have run it two at a time - the latency cause the `defects` round already
identified, which would then have dominated this round's wall clock for a reason that has nothing
to do with decomposition.

`parallel` was raised to 8 (the planner decides how wide the work divides; the scheduler should not
silently quarter it) and the round restarted. **This amends the held-fixed table above the divider,
which the reporting form otherwise forbids.** It is legitimate only because no result existed yet,
and it is recorded here rather than made quietly. Nothing was amended after a number was visible.

Raising it does NOT make a gate node concurrent: `Coordinator.gate` runs its subprocess
synchronously on the event loop, so a gate still blocks every in-flight node (`OPEN-WORK` 65). That
is untouched, and this round does not test it.

### What is NOT a controlled comparison here, stated first

**This round is not a controlled delta from the `defects` round.** Three things changed at once:
the case; agentdag's limits (`charged_tokens` now excludes cache reads, `max_turns` 25 to 2000, and
a 300,000 per-node default where planner-emitted nodes previously had none); and the scheduler's
concurrency default, 2 to 8. The `agentswarm` cases tree also moved, `5a1c9ea` to `071f36c`.

So the agentdag number here may NOT be compared with the agentdag number from the `defects` round.
What is internally valid is the arm-vs-arm comparison INSIDE this round, because both arms get the
same case, ceiling, deadline and model tier. Anything else is a different experiment.

### Why 1,200,000 and not the protocol's 600,000

600,000 is the figure `agentswarm` round 10 was calibrated at, and it is right for `defects`. It is
wrong here for a mechanical reason: the per-node budget is now 300,000, so a 600,000 run ceiling
buys two node-budgets and the fan-out that makes a coordinator worth having cannot happen. The
ceiling is doubled so the per-node bound is the thing being exercised rather than the run ceiling
truncating the plan at its second node.

The cost of that choice is stated rather than hidden: it breaks numeric comparability with
`agentswarm` round 10 and with last night's round. It is the run ceiling that moved, and both arms
moved together.

### Token accounting

Both arms are counted as `input_tokens + cache_creation_input_tokens`, keyed by dispatch, cache
reads excluded - the protocol's definition, applied externally to both.

agentdag's OWN charge now also includes output tokens (`charged_total`, shipped 2026-09-03), a
deliberate divergence documented in that function: agentdag reads the terminal `ResultMessage`
usage, which is cumulative and accurate, so the protocol's reason for excluding output does not
apply to it. That affects what agentdag's internal budget bounds, NOT the figure reported here,
which is the protocol's.

### Deviations, stated in advance

* **The workspace is copied in by the run itself**, for both arms equally. `plan-goal` mints its
  own empty `wt/root` and takes only a goal string, so neither arm is handed a pre-seeded
  directory; both are told to copy it as step 0.
* **One run per arm**, so any difference smaller than the run-to-run spread of either is
  indicative and not a result.

### What each outcome band will mean

| Band                                               | Reading                                                                                                                                                 |
|----------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------|
| both score 0 or near it                            | **MIS-CALIBRATED** - 1,200,000 is below this case's floor for both, and the run says nothing about either system                                        |
| both score at or near 81                           | **MIS-CALIBRATED** - saturated, the failure mode the `defects` round already hit                                                                        |
| both land roughly 15..65                           | the intended discriminating band; read `score_per_mtok`, `score_per_minute` and quality together                                                        |
| agentdag higher at equal or lower cost per point   | the first real evidence for the coordinator on a non-saturating case - still one run, still indicative                                                  |
| the single agent higher at equal cost              | decomposition is not repaying its overhead on a case explicitly built to exceed one agent, which is the strongest available evidence against the thesis |
| either arm's hidden suite ERRORS rather than fails | read the two apart: all-errored means the tree would not import, all-failed means the work was not done                                                 |

### Coordination metrics

A dash for both arms, never a zero. Undefined for a DAG in fixed order and for an agent with no
peers, and a system scores perfectly on all of them by doing nothing.

## Results

Written after the run. Nothing above this divider was edited.

### Verdict: VOID

Three reasons, and any one of them is sufficient on its own. The third is the one that decides
what comes next.

1. **Arm A crashed** on a kernel defect, 14 minutes in, after 3 of its planner's 12 nodes.
2. **The held-fixed `worker model tier` row was false when it was written**, not broken by the
   run: agentdag's planner picks a `tier_role` per node and the shipped policy maps that to a
   model row, so arm A ran on three different models while the control was pinned to one.
3. **The control SATURATED at 81/81**, which is the pre-registered band reading
   "MIS-CALIBRATED - saturated, the failure mode the `defects` round already hit". The case's own
   task text says "There is more here than one agent can finish"; at this ceiling, with the
   protocol's re-prompting, that is refuted.

### What ran

Arm A 12:14:10 to 12:28:06 CEST, arm B 12:29:54 to 13:13:51, sequentially as pre-registered.
agentdag at `beab496` for arm A, which is BEFORE the fix named below. Both runners exited 0.

The `agentswarm` checkout was at `7541f70`, ahead of the pre-registered `071f36c`, so the
difference was measured rather than assumed: `git diff 071f36c HEAD -- cases/spec
src/agentswarm/cases.py src/agentswarm/quality.py` is empty, so the material is byte-identical to
the pin.

Checked before either arm, on the copy each arm was told to seed from, not merely in the
`agentswarm` repo:

* floor 0/81, with all 81 FAILED and 0 errors - the tree imports and the work is simply not done;
* the visible gate green on the untouched seed at 92 passed, exactly as the table above states;
* the seed hashed to a 14-file manifest, re-checked after arm A and unchanged, so neither arm
  mutated the source both were copying from.

### 1. What arm A did before it crashed

The planner produced a 12-entry DAG, and it was a reasonable one: a seed node, two foundation
nodes depending on it, a six-wide fan-out depending on both of those, a gate over the fan-out, an
integrate node, and a final gate. Three nodes ran. The coordinator then died with

```
run <id> failed: node 'n-0005' depends on 'n-0002', which this run has not dispatched
```

`n-0002` was running at that moment and finished normally three minutes later.

**Root cause.** `_ready` decided a dep was satisfied when it was no longer PENDING, and an entry
leaves the pending map the moment it is LAUNCHED. So a dep that was merely in flight read exactly
like a dep belonging to another plan, which is the case that rule was written for. The dependent
was launched on that reading, reached the dispatcher before its dep had a record, and the
dispatcher refuses that with a `KernelError` that fails the run. Fixed in `c446771` by asking the
plan's own entry set, taken once before anything launches.

**The defect is old; what made it reachable is recent.** At `parallel = 2` the dependent queues on
the shared semaphore behind the running dep and picks up its record on the way through, so the
shipped default hid it. Raising that default to 8 - the amendment recorded above the divider, made
for this round - freed a slot for the dependent to reach the dispatcher first. So the amendment
did not cause the defect and did not merely expose it in the abstract: it is why this round met it
and the `defects` round did not.

### 2. The model tier was never held fixed

| node     | plan `tier_role` | model resolved | new tokens |
|----------|------------------|----------------|------------|
| `p_root` | planner          | fable          | 20,652     |
| `n-0001` | standard         | sonnet         | 41,056     |
| `n-0002` | deep             | opus           | 81,677     |
| `n-0003` | deep             | opus           | 69,995     |

The control is pinned to `model="sonnet"` in its runner. So the most expensive axis in the
comparison differed between the arms while the held-fixed table claimed it did not. This is not
something a re-run repairs, which is why the round is void rather than repeated.

### 3. The control saturated, and that is the finding

One sonnet agent, re-prompted whenever budget remained, reached **81/81** in 44 minutes for
760,578 new tokens. It was stopped by the wall-clock deadline at 63.4% of the token ceiling, not
by its own judgement, so the score is a floor on what it would have reached rather than a ceiling.

`spec` was chosen precisely because it was expected NOT to saturate: 81 hidden tests against
`defects`'s 20, a measured floor of 0, and a task text stating outright that there is more here
than one agent can finish. At a 1,200,000-token ceiling with re-prompting, that expectation is
refuted. The case cannot discriminate at this ceiling, because a perfect coordinator arm could at
best tie.

Note which mechanism did the work, because it is the same one the `defects` round identified: the
protocol's re-prompt loop. Ten prompts were sent. On `defects` the same arm left to judge itself
stopped after one turn having changed nothing, and re-prompting took it from 0/20 to 19/20. Here
re-prompting took it to a perfect score on a case built to be unfinishable by one agent. The
stopping rule keeps turning out to be the largest single effect either round has measured, and it
is not the effect either round set out to measure.

### Not scored: quality

The pre-registration says to score quality against `cases/spec/hidden/reference`. That was NOT
run. For a from-scratch case the quality number is a DELTA between comparable runs, by
`quality.py`'s own account, and there is no comparable pair here: one arm crashed a quarter of the
way into its plan. Scoring it would produce a number with nothing to subtract it from, and the
`defects` round already measured this instrument reading the same untouched tree as 4.41 and 5.09.

### Apparatus note, affecting both arms equally

`pytest` on this machine's PATH is broken - its shebang names an interpreter that no longer
exists - so the bare `pytest tests/ -q` the case specifies fails with exit 126 for a reason that
has nothing to do with either arm's work. Both arms met it and both worked around it; arm A's node
transcripts record the failure and the workaround. The gate figures above were taken with a
working interpreter running the same suite. It is recorded because it consumed some of both arms'
budget, not because it favoured either.
